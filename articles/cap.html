Cap

Deux erreurs très ordinaires mises bout à bout : une référence d'objet qu'on peut changer dans l'URL, et une capability Linux accordée à un binaire qui n'en avait pas besoin.

La chaîne en cinq lignes

Le résumé avant le détail, pour que quelqu'un qui ne fera pas la machine comprenne quand même de quoi il s'agit.

  • Trois services exposés, FTP, SSH et un serveur web d'administration
  • Un identifiant de capture réseau modifiable dans l'URL, qui donne accès à celle d'un autre utilisateur
  • Des identifiants en clair dans le trafic capturé, réutilisables en SSH
  • Une capability Linux posée sur un binaire, qui suffit à devenir root

Reconnaissance

Un scan de ports complet suivi d'une détection de version sur les ports ouverts suffit pour cadrer la machine. 

# Balayage réseau et détection de services
ports=$(nmap -p- --min-rate=1000 -Pn -T4 10.10.10.245 | grep '^[0-9]' | cut -d '/' -f 1 | tr '\n' ',' | sed s/,$//)
nmap -p$ports -Pn -sC -sV 10.10.10.245

Trois services ressortent : vsftpd 3.0.3 sur le port 21 (accès anonyme désactivé), OpenSSH 8.2p1 sur le port 22, et un serveur applicatif Gunicorn sur le port 80 qui héberge un tableau de bord d'analyse réseau.

Énumération

Le site web permet de lancer des captures réseau de 5 secondes, chacune rattachée à un identifiant numérique consultable via /data/<id>. Rien n'empêche de revenir en arrière sur cet identifiant : c'est un IDOR (Insecure Direct Object Reference) classique, où l'autorisation repose uniquement sur le fait de connaître l'URL.

Accès initial

En remontant jusqu'à /data/0, on récupère la toute première capture enregistrée au démarrage du serveur, avant même la mienne. Son ouverture dans Wireshark (ou directement via tshark) révèle un échange FTP en clair. 

# Extraction des identifiants non chiffrés dans la capture réseau 0
tshark -r capture_0.pcap -Y 'ftp' -T fields -e ftp.request.command -e ftp.request.arg
→ Utilisateur : nathan / Mot de passe : Buck3tH4TF0RM3!

Le mot de passe FTP est réutilisé tel quel sur SSH : 

ssh nathan@10.10.10.245

Élévation de privilèges

Une fois sur la machine, LinPEAS signale une capacité Linux inhabituelle posée directement sur l'interpréteur Python système. On peut vérifier ça soi-même avec getcap : 

# Audit des capacités Linux assignées aux binaires
getcap -r / 2>/dev/null
→ /usr/bin/python3.8 = cap_setuid,cap_net_bind_service+eip

cap_setuid permet à n'importe quel processus lancé avec ce binaire de changer son UID effectif vers 0, sans avoir besoin du bit SUID classique. Python devient alors un raccourci direct vers root : 

# Preuve de concept d'élévation vers l'UID 0 (Root)
/usr/bin/python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash")'
whoami && id
→ root (uid=0(root) gid=1001(nathan) groups=1001(nathan))

Ce que j'en retiens

Deux défauts très banals, pris séparément, ne mènent nulle part. C'est leur combinaison qui compromet la machine : l'IDOR n'a de valeur que parce que la capture fuite des identifiants en clair, et ces identifiants n'ont de valeur que parce qu'ils sont réutilisés sur un service distinct. Côté remédiation, trois points ressortent : retirer la capacité cap_setuid de l'interpréteur Python (setcap -r /usr/bin/python3.8), mettre un contrôle d'accès sur les routes /data/<id> pour qu'un utilisateur ne puisse consulter que ses propres captures, et abandonner FTP en clair au profit de SFTP ou FTPS.
