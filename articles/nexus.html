Nexus

La machine qui rappelle qu'un dépôt Git public n'est pas seulement du code : c'est aussi l'historique de tout ce qu'on y a commité par erreur.

La chaîne en cinq lignes

Le résumé avant le détail, pour que quelqu'un qui ne fera pas la machine comprenne quand même de quoi il s'agit.

  • Un service Gitea exposé, dont un dépôt laisse fuiter des identifiants
  • Une offre d'emploi publiée qui donne le format des noms d'utilisateur
  • Un CRM Krayin vulnérable à CVE-2026-38526, qui donne un shell en www-data
  • D'autres identifiants dans les fichiers de configuration du CRM, utilisables en SSH
  • Un service de synchronisation de templates vulnérable au path traversal, qui mène à root

Reconnaissance

Le serveur HTTP Nginx redirige vers le domaine nexus.htb, à ajouter dans /etc/hosts. La page de recrutement de l'entreprise fictive donne au passage un contact RH (j.matthew@nexus.htb), utile pour la suite.

Le dépôt Gitea

Un fuzzing de sous-domaines (vHost) sur nexus.htb révèle deux services additionnels : git.nexus.htb, une instance Gitea, et billing.nexus.htb, un CRM Krayin en version 2.2.0. 

# Découverte des sous-domaines via ffuf
ffuf -w /usr/share/wordlists/seclists/Discovery/DNS/bitquark-subdomains-top100000.txt:FFUZ \
  -u http://nexus.htb/ -H 'Host: FFUZ.nexus.htb' -fw 4
→ git.nexus.htb (200), billing.nexus.htb (200)

Sur Gitea, le dépôt public admin/krayin-docker-setup expose un fichier .env. Le fichier actuel est propre, mais l'historique des commits ne l'est pas : un ancien commit contient un mot de passe qui a ensuite été retiré du code sans jamais être changé côté application. Parcourir l'historique Git d'un dépôt public fait partie de l'énumération, pas seulement lire le code courant.

Construire la liste d'utilisateurs

Avec le mot de passe fuité et l'adresse e-mail trouvée sur la page de recrutement, il devient possible de s'authentifier sur le CRM Krayin avec le compte j.matthew@nexus.htb.

Accès initial

L'éditeur de courriels intégré à Krayin embarque TinyMCE, vulnérable à CVE-2026-38526 : une faille de téléversement de fichier qui permet de déposer un script directement dans un répertoire servi publiquement par le CRM. 

# Téléversement via TinyMCE (POST /admin/tinymce/upload)
# fichier déposé dans /storage/tinymce/<hash>.php
curl -s 'http://billing.nexus.htb/storage/tinymce/779bc2392c37c0e8f842b3a6af0a4d8e.php?cmd=id'
→ uid=33(www-data) gid=33(www-data) groups=33(www-data)

Passage utilisateur puis root

Le fichier /var/www/billing/.env, lisible depuis ce shell www-data, contient cette fois les identifiants de la base de données en cours d'usage. Réutilisés, ils donnent un accès SSH au compte système jones.

Sur la machine, un timer systemd (gitea-template-sync.timer) exécute toutes les deux minutes un script, /etc/gitea/template-sync.py, sous l'identité root. Ce script construit des chemins de fichiers avec os.path.join en utilisant directement la sortie brute de git ls-tree, sans filtrer les séquences ... En forgeant un objet Git dont l'arborescence remonte plusieurs niveaux (.. / .. / root / .ssh / authorized_keys) et en le poussant sur le dépôt de template synchronisé, le script root écrit lui-même une clé SSH publique arbitraire dans /root/.ssh/authorized_keys. 

# Forge d'un objet Git avec séquences de traversée relatives,
# arborescence : tree -> .. -> .. -> root -> .ssh -> authorized_keys
git push -u origin main --force
→ clé publique écrite dans /root/.ssh/authorized_keys

ssh -i /tmp/.k root@nexus.htb
whoami && id
→ root (uid=0(root) gid=0(root) groups=0(root))

Ce que j'en retiens

La machine entière repose sur des traces qu'on laisse derrière soi : un secret retiré du code mais jamais purgé de l'historique Git, une sortie de commande considérée comme fiable alors qu'elle vient d'un dépôt que n'importe qui peut pousser. Les correctifs vont dans ce sens : restreindre les types de fichiers acceptés par l'upload TinyMCE aux formats image stricts, vérifier dans template-sync.py que le chemin résolu reste confiné au répertoire de staging, et purger l'historique des commits Git avec un outil comme git-filter-repo plutôt que de se contenter de supprimer le fichier en surface.
