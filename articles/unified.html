Unified

La machine qui m'a fait comprendre Log4Shell autrement qu'en lisant un article. Une console d'administration réseau, une chaîne de caractères dans un en-tête, et le serveur va chercher du code ailleurs.

La chaîne en cinq lignes

Le résumé avant le détail, pour que quelqu'un qui ne fera pas la machine comprenne quand même de quoi il s'agit.

  • Un portail UniFi Network exposé derrière un proxy HTTP
  • Une version vulnérable à CVE-2021-44228, dite Log4Shell
  • L'injection passe par un en-tête POST, pas par un champ du formulaire
  • Une base MongoDB accessible localement, où le hash du mot de passe administrateur peut être remplacé
  • Le panneau d'administration livre ensuite un mot de passe SSH

Reconnaissance

Le contrôleur réseau UniFi Network, en version 6.4.54, est exposé sur le port HTTPS 8443. Cette version embarque une version vulnérable d'Apache Log4j, le fameux CVE-2021-44228 (« Log4Shell »).

Comprendre Log4Shell

Log4j journalise des chaînes de caractères fournies par l'utilisateur sans toujours les traiter comme de simples données. Quand une valeur ressemble à ${jndi:ldap://...}, certaines versions vulnérables vont réellement résoudre ce lookup JNDI, c'est-à-dire aller interroger un serveur LDAP distant et charger ce qu'il leur répond. Sur UniFi, le champ visé n'est pas un champ de formulaire visible, mais l'en-tête remember envoyé dans la requête POST /api/login.

Mise en place

Déclencher la faille nécessite un service qui répond aux lookups JNDI (un serveur LDAP ou HTTP de référence) et un payload qui, une fois résolu, force le serveur Tomcat sous-jacent à instancier un objet sérialisé malveillant. 

# Constat d'audit : injection JNDI sur l'authentification UniFi
→ Paramètre : 'remember' dans POST /api/login
→ Mécanisme : résolution JNDI non assainie par Log4j (LDAP)
→ Preuve : requête de rappel reçue sur le serveur d'écoute

Exploitation

Une fois la charge envoyée dans l'en-tête, Tomcat instancie le processus système porté par l'objet sérialisé, ce qui donne un accès initial interactif sous l'identité de service unifi — un compte non privilégié, mais suffisant pour continuer l'énumération locale.

Élévation de privilèges

Le serveur héberge une instance MongoDB locale (port 27117, base ace) sans authentification activée. Avec un accès direct en écriture à la collection des administrateurs, il est possible de remplacer le hash SHA-512 du mot de passe administrateur par un hash dont on connaît le mot de passe en clair. 

# Preuve de concept de l'élévation administrative
1. Calcul d'une empreinte SHA-512 pour un mot de passe choisi
2. Écriture de l'attribut x_shadow du compte administrator dans MongoDB
3. Connexion au portail d'administration UniFi avec ce nouveau mot de passe

Une fois dans le tableau de bord d'administration, la section de gestion des équipements (« Device Authentication ») affiche en clair le mot de passe root utilisé pour administrer les points d'accès par SSH — et ce même mot de passe est celui du compte root du système lui-même. 

ssh root@10.129.96.149
whoami && id
→ root (uid=0(root) gid=0(root) groups=0(root))

Ce que j'en retiens

C'est la machine qui m'a fait vraiment comprendre pourquoi Log4Shell a eu un tel impact : n'importe quelle chaîne journalisée, même dans un en-tête HTTP anodin, pouvait devenir un point d'entrée. La suite de la chaîne, elle, tient à des pratiques bien plus ordinaires : une base locale sans authentification et un mot de passe affiché en clair dans une interface d'administration. Les correctifs : mettre à jour UniFi Controller vers une version supérieure ou égale à 6.5.55 (qui désactive formatMsgNoLookups par défaut), activer l'authentification sur l'instance MongoDB locale, et chiffrer au repos les mots de passe de gestion des équipements plutôt que de les stocker en clair.
