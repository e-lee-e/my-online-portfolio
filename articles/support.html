Support

La seule machine Windows de la série, et celle qui rejoint le plus mes TP sur Active Directory. On y passe d'un partage ouvert à un contrôle complet du contrôleur de domaine.

La chaîne en cinq lignes

Le résumé avant le détail, pour que quelqu'un qui ne fera pas la machine comprenne quand même de quoi il s'agit.

  • Un partage SMB accessible sans authentification
  • Un exécutable déposé sur ce partage, qui interroge l'annuaire LDAP
  • Le mot de passe de liaison LDAP, récupérable par rétro-ingénierie, analyse réseau ou émulation
  • Un mot de passe laissé dans un champ de description de compte, exploitable en WinRM
  • Une relation d'objets révélée par BloodHound, puis une délégation contrainte basée sur les ressources

Reconnaissance

La cible héberge un contrôleur de domaine Active Directory. Comme souvent sur ce type de machine, l'énumération commence par les services d'annuaire et de partage de fichiers plutôt que par un site web.

Le partage SMB

Un partage public accessible sans authentification contient un exécutable d'inventaire, UserInfo.exe. La décompilation de ce binaire .NET met en évidence une méthode Protected.getPassword() qui reconstruit un mot de passe à partir d'un contenu encodé en Base64, lui-même déchiffré par un double XOR avec une clé statique codée en dur. Le compte de service visé est support\ldap.

Un chiffrement « maison » codé en dur côté client n'est pas un mécanisme de sécurité : dès qu'un attaquant a le binaire, il a aussi la clé.

Récupérer le mot de passe de liaison

Une fois la routine de déchiffrement reconstituée (à la main, en réimplémentant la logique du double XOR, ou en exécutant simplement le binaire dans un environnement contrôlé), le mot de passe du compte support\ldap est en clair.

Énumération LDAP

Ces identifiants donnent un accès en lecture à l'annuaire. L'inspection des attributs étendus des comptes révèle que l'attribut descriptif info du compte support contient lui aussi son mot de passe en clair — une pratique de stockage très répandue en entreprise et tout aussi dangereuse. Ce compte ouvre une session d'administration à distance via WinRM (port 5985). 

# Constat d'audit
→ Objet : CN=support,CN=Users,DC=support,DC=htb
→ Attribut 'info' : mot de passe en clair
→ Accès obtenu : session WinRM (support\support)

Élévation de privilèges

Une cartographie BloodHound des relations d'accès Active Directory montre que le groupe Shared Support Accounts dispose du privilège GenericAll sur l'objet du contrôleur de domaine lui-même. C'est la clé d'une attaque par délégation contrainte basée sur les ressources (RBCD) : 

# Preuve de concept méthodologique RBCD
1. Exploitation du quota ms-DS-MachineAccountQuota pour créer un compte machine
2. Définition de msDS-AllowedToActOnBehalfOfOtherIdentity sur le contrôleur de domaine
3. Forge d'un ticket Kerberos S4U2self / S4U2proxy usurpant Administrator
4. Exécution distante sous le contexte NT AUTHORITY\SYSTEM

Avec GenericAll sur le DC, on peut créer un compte ordinateur (le quota par défaut l'autorise), lui attribuer une délégation contrainte sur le contrôleur de domaine, puis forger une chaîne de tickets Kerberos qui usurpe le compte Administrateur du domaine. Le résultat est une exécution de commandes sous l'identité la plus élevée possible.

Ce que j'en retiens

Trois défauts d'hygiène Active Directory classiques, empilés : un partage ouvert qui n'aurait pas dû contenir de binaire exposant des secrets, un mot de passe recopié dans un champ texte libre de l'annuaire, et une permission GenericAll accordée sans justification métier sur l'objet le plus sensible du domaine. Les correctifs : ramener ms-DS-MachineAccountQuota à 0, retirer GenericAll au groupe support sur le contrôleur de domaine, et purger les attributs description / info de l'annuaire de tout mot de passe en clair.
